# Эксплуатация

## Учётные записи

Первый запуск создаёт `admin` со случайным паролем, он один раз пишется в
журнал службы:

```bash
ssh deploy journalctl -u smartsale | grep пароль
```

Остальные заводятся в кабинете. Агентов — на странице «Агенты», пароль
показывается один раз при создании и при сбросе.

**Пароли агентам придумывать простыми.** Случайный вида `4Q4fX4Zuvg`
набирается на телефонной клавиатуре с переключением регистра, и это уже
стоило трёх неудачных входов подряд. Строчные буквы и цифры — достаточно.

Агент в веб-кабинет не пускается: его инструмент — телефон, а кабинет
показывает чужие заказы и настройки.

## Роли

| Роль | Что доступно |
|---|---|
| `admin` | всё, включая заведение агентов и отключение устройств |
| `supervisor` | заказы только своих агентов |
| `operator` | заказы, клиенты, цены, остатки; без настроек |
| `warehouse` | только отгрузка |
| `agent` | ничего в кабинете, работает через приложение |

## Потерянный телефон

Кабинет → «Агенты» → «Отключить» у нужного устройства. Токен гасится
немедленно, войти заново с этого аппарата нельзя даже с верным паролем.
Заказы при этом не теряются: они привязаны к агенту, а не к устройству.

## Разбор жалоб

**«Заказ не дошёл».** Кабинет → «Обмены». Там видно каждое обращение
телефона: когда была связь, когда забирал справочники, что присылал. Если
обращений нет вовсе — телефон до сервера не доходил, дело в связи или в
отключённом устройстве.

**«У меня старые цены».** Там же, столбец «последний забор справочников».

**«Агент молчит».** На сводке отдельно перечислены агенты, чьи телефоны не
выходили на связь больше суток. Их заказы лежат в аппаратах и в офисе не
видны — чем позже это заметят, тем позже поедет машина.

**Заказ отклонён.** Причина показывается агенту в приложении дословно и
хранится в самом заказе на телефоне. Типичные: клиент в стопе, превышен
кредитный лимит, у клиента не задан вид цены.

## Наличные у агентов

Собранные агентом наличные висят на нём до инкассации. Видно на сводке и на
странице «Агенты», там же кнопка «Принять в кассу». Без этой отметки не
понять, сколько денег у агента на руках прямо сейчас.

## Демонстрационные данные

```bash
ssh deploy 'cd /srv/smartsale/app_src && set -a && . /srv/smartsale/.env && set +a && runuser -u smartsale -- env DATABASE_URL="$DATABASE_URL" SECRET_KEY="$SECRET_KEY" /srv/smartsale/venv/bin/python tools/seed_demo.py'
```

Без ключей скрипт откажется работать на непустой базе. `--force` дозаполняет
поверх существующего.

**Данные вымышленные**: ассортимент, цены, названия магазинов и ФИО
придуманы для показа работы приложения и не описывают никакую реальную
торговую сеть. Перед боевым запуском заменить целиком.

## Обновление приложения

```bash
scp -r app deploy:/srv/smartsale/app_src/ && ssh deploy systemctl restart smartsale
```

Схема базы создаётся через `create_all` — **изменения моделей до
существующей базы не доедут**. При правке моделей переводить на alembic.

## Резервного копирования нет

`mon-backup.timer` на сервере копирует только проект мониторинга. Базы
`smartsale`, `tabel` и `zp` не выгружаются никуда — при потере диска
пропадут вместе с заказами, отгрузками и оплатами.

Минимум, который стоит завести: ежедневный `pg_dump` всех трёх баз в
`/srv/backup` и забор оттуда на рабочую машину, рядом с тем, как это уже
сделано для мониторинга.
