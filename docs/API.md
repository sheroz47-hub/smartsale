# API мобильного приложения

Версия протокола `1.0`. Все ответы — JSON в UTF-8.

Приложение присылает свою версию протокола при входе. Расхождение по
старшей части означает, что приложение надо обновить: сервер отвечает `426`
и текстом для агента. Молча работать с чужим форматом опаснее, чем отказать.

## Устройство обмена

Односторонний по каждому виду данных: справочники агент только читает,
документы только создаёт. При таком разделении слияния изменений не
возникает вовсе — а слияние и есть самое дорогое в офлайн-приложениях.

Забор справочников инкрементальный. Телефон присылает время прошлого обмена
(`since`) и получает изменившееся после. Время всегда серверное, из
предыдущего ответа: часы на телефонах уходят на минуты, доверять им нельзя.

Отметка времени отдаётся в UTC с суффиксом `Z`, а не `+00:00`. Плюс в строке
запроса означает пробел, и клиент, забывший его закодировать, получал бы
отлуп на ровном месте. Разбор `since` этот случай всё равно переживает.

## Авторизация

```
POST /api/v1/auth/login
{
  "login": "agent.karimov",
  "password": "...",
  "device_id": "<UUID, создаётся приложением при установке>",
  "device_name": "Xiaomi 24117RN76G",
  "app_version": "1.0.0",
  "protocol": "1.0"
}
```

Ответ:

```json
{
  "token": "<id устройства>.<секрет>",
  "protocol": "1.0",
  "server_time": "2026-08-14T07:13:56.444760Z",
  "currency": "UZS",
  "user": {"uuid": "...", "full_name": "Каримов Азиз Рустамович", "login": "agent.karimov"}
}
```

Дальше токен идёт заголовком `Authorization: Bearer <token>`.

Токен хранится на сервере хешем, как пароль: база с токенами в открытом виде
— это готовый доступ ко всем учёткам агентов. Восстановить выданный токен
нельзя, потерянный означает повторный вход по паролю.

Устройство создаётся при первом входе и живёт до отключения администратором.
Повторный вход с того же аппарата перевыпускает токен — так агент
восстанавливается после переустановки приложения, не дожидаясь никого.
Отключённое устройство паролем не воскрешается: отключают его обычно потому,
что телефон потерян.

| Код | Когда | Что делает приложение |
|---|---|---|
| `401` | неверный пароль либо токен отозван | просит войти заново |
| `403` | устройство отключено, либо вход не агента | сообщает обратиться к администратору |
| `426` | версия протокола устарела | требует обновить приложение |

Причина отказа приходит в поле `detail`, и приложение показывает именно её.
Собственный текст по коду ответа — только когда сервер промолчал: один и тот
же `401` приходит и на неверный пароль при входе, и на отозванный токен при
обмене, а догадка приложения в первом случае прямо врала агенту.

## Забор справочников

```
GET /api/v1/sync/pull?since=<ISO-8601 UTC>
```

Пустой `since` — первый обмен, отдаётся всё.

Возвращаются: `warehouses`, `price_types`, `categories`, `products`,
`prices`, `stocks`, `customers`, `routes`, а также `server_time` и признак
`more`.

`more: true` означает, что выдача упёрлась в размер страницы
(`SYNC_PAGE_SIZE`, по умолчанию 1000). Телефон должен сразу повторить запрос
с новым `since`, не дожидаясь расписания, иначе на большом каталоге агент
уйдёт в поле с его началом.

Клиенты приходят только свои — закреплённые за этим агентом. Чужая
клиентская база ему не нужна, а на телефоне это ещё и лишние мегабайты.

Отключённые записи приходят вместе с активными, с `active: false`. Телефон
обязан их погасить, а не просто не увидеть: иначе снятый с продажи товар
останется в каталоге навсегда.

Долг и просрочка по клиенту приходят посчитанными сервером. На телефоне их
считать не по чему — отгрузок и оплат других агентов он не видит.

**Все денежные величины и количества — строки.** JSON не различает 1.10 и
1.1, а разбор чисел с плавающей точкой на телефоне даёт свою погрешность.
Строка доезжает ровно такой, какой ушла, и на устройстве кладётся в
`BigDecimal`.

## Отправка документов

```
POST /api/v1/sync/push
{
  "orders":   [...],
  "payments": [...],
  "visits":   [...]
}
```

У каждого документа есть `client_uid` — его генерирует телефон. Связь на
рынке рвётся посреди отправки, телефон повторяет запрос, и без ключа
идемпотентности в базе появлялись бы двойные заказы. Повторная отправка того
же `client_uid` возвращает результат первой, а не создаёт второй документ.

Ответ — по документу на каждый присланный:

```json
{"client_uid": "...", "status": "accepted", "number": "З000015", "state": "new"}
{"client_uid": "...", "status": "rejected", "error": "отгрузка клиенту «...» запрещена: просроченный долг"}
```

Каждый документ обрабатывается отдельно и отвечает за себя: один отклонённый
заказ не роняет весь пакет. Телефон по ответу решает, что убрать из очереди,
а что показать агенту.

Отклонённый документ приложение не удаляет и повторно не отправляет: причина
не в связи, а в существе — клиент в стопе, превышен лимит, снятый товар.
Решать это агенту, а не приложению.

## Состояние ранее отправленного

```
GET /api/v1/orders/state?since=<ISO-8601 UTC>
```

Агенту в точке нужно знать, отгрузили ли прошлый заказ и не отменил ли его
офис. Отдельным запросом, а не в общем `pull`: список коротких записей
меняется чаще справочников, и тянуть его можно чаще.

## Проверка связи

```
GET /api/v1/ping
```

Без авторизации намеренно: приложению нужно уметь отличать «нет сети» от
«не тот пароль» до всякого входа.

## Правила приёма заказа

Проверяются при приёме, а не при отгрузке. Сказать агенту «клиент в стопе»,
пока он стоит в точке, полезно — он поговорит о долге на месте. Узнать это
через два дня на складе бесполезно.

- клиент существует, активен и не в стопе;
- в заказе есть строки, у каждой ненулевое количество и заданная цена;
- при безналичной оплате долг вместе с новым заказом не превышает лимита
  клиента; при оплате наличными лимит не проверяется — платят при отгрузке.
