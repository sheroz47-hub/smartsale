# Рабочие места менеджера (АРМ) и доработки — проект

Черновик к утреннему разбору. Собран автономно 17–18.09.2026 по: выгрузке
коммерческой обработки **«Интеграция Моби-С с 1С:УТ11»** (102 формы, модуль
~18 000 строк — изучен тремя под-агентами), выгрузке конфигурации УТ (проверено
кодом/константами), процессным документам «Стандарт работы ТП» и «Процедура
работы ТК_РДБ».

---

## 0. ГЛАВНЫЙ ВЫВОД ИЗ РАЗБОРА МОБИ-С (архитектура)

**Моби-С — это ОДНА внешняя обработка `.epf`, которая НЕ добавляет своих объектов
в конфигурацию и всё строит на ТИПОВЫХ объектах УТ.** Где что лежит у них:

| Что | Где в Моби-С (типовое!) |
|---|---|
| Настройки продукта (агенты, ключи, карты документов, параметры устройств) | `ХранилищеОбщихНастроек`, владелец `"MobiS"`, привил. режим |
| Агент | `Справочник.Пользователи` (обычный юзер ИБ) + массив ссылок в настройке `СписокАгентов` |
| Атрибуты объектов (тип агента, статус документа, привязки) | штатный `РегистрСведений.ДополнительныеСведения` (свойства ПВХ создаются на лету) |
| Координаты клиентов | штатная `КонтактнаяИнформация` (свои виды КИ, тип «Другое», создаются на лету) |
| Задания/визиты/маршруты | штатный `Документ.ЗаданиеТорговомуПредставителю` (шапка + ТЧ «Задачи») |
| Доставка | штатные `Документ.ЗаданиеНаПеревозку` + `ПоручениеЭкспедитору` |
| Ассортимент/MML | штатные `РегистрСведений.Ассортимент` + `Документ.ИзменениеАссортимента` + `ФорматыМагазинов` (=каналы сбыта) |
| Реализации/заказы из выгрузки | обобщённое создание `докОбъект` по **настраиваемой карте** «мобильный тип → документ УТ + вариант» |
| Фото, треки, логи | файлы на диске (каталог агентов) + внешняя `mobi_s.sqlite3` |
| Права рабочих мест | свой реестр «функций», `ПроверитьРазрешение(ИмяФормы)` на входе в форму |

**Что это значит для нас.** Мы пошли ДРУГИМ путём — расширение конфигурации со
своими объектами (`SmartSale_Задания`, `SmartSale_Маршруты`, `SmartSale_Токены`,
`SmartSale_СкладыАгентов`, `SmartSale_Акции`, `SmartSale_ВопросыАудита` и др.).
Это уже построено и работает. Полностью переходить на архитектуру Моби-С (чистый
`.epf` на типовых объектах) = переделать весь обмен — не нужно. Но при
проектировании АРМ полезно взять их приёмы (см. ниже по каждому), а по паре
объектов встаёт **реальная развилка** — типовой объект vs наш (задания, MML).

---

## 1. Зачем это и рамка

Построена «половина» SFA: **телефон агента** ↔ **сервер-шина** ↔ **УТ**. Не
хватает **рабочих мест менеджера в самой УТ** (чем в Моби-С пользуется
супервайзер/оператор): настроить маршруты, поставить задания, задать обязательный
ассортимент, отгрузить заказы, подключить агента.

**Ограничение (не меняется).** Формы/обработки в 1С собираешь и грузишь ты; от
меня — исходники `.bsl` + структуры форм + шаги. Живую форму я не вижу — интерактив
(карта, сканер) отлаживаешь ты.

## 4. АРМ №4 — «Реализация на основании заказов» ✅ (рекомендую первым)

Чистая польза складу/оператору, штатные средства, без карты и APK.

**Механизм (проверен кодом).** У `РеализацияТоваровУслуг` — штатная
`ОбработкаЗаполнения → ЗаполнитьДокументНаОснованииЗаказаКлиента`
(`РеализацияТоваровУслуг/ObjectModule.bsl:990`), у `ЗаказКлиента` — команда
`ДобавитьКомандуСоздатьНаОснованииЗаказа` (`ManagerModule:306`). Создать
реализацию на основании — одна строка:

```
РеализацияОбъект = Документы.РеализацияТоваровУслуг.СоздатьДокумент();
РеализацияОбъект.Заполнить(СсылкаНаЗаказКлиента);   // партнёр, договор, товары, цены
РеализацияОбъект.Записать(РежимЗаписиДокумента.Проведение);  // опционально
```

**Приём от Моби-С (взять):** карта соответствия «мобильный тип → документ УТ +
**вариант**» (`ОбработкаВыгруженныхДокументов` / настройка `ПостобработкаДокумента`):
из заказа можно делать Реализацию / Заказ клиента / Чек ККМ — выбирается
настройкой, «для всех» или пер-агента, а не хардкодом. Создание — обобщённо (один
`докОбъект` по типу), статус пишется обратно (у них — в доп.сведения; у нас — в
`SmartSale_ЖурналПриема`/статус заказа).

**АРМ:** список заказов «к отгрузке» (отбор: агент, дата, статус, склад) → отметить
→ «Создать реализации» пачкой (создать+провести) → лог построчно (создано/номер/
ошибка).

**Решить:** роль оператора (права проведения реализации); проводить сразу или
черновиком; поток статусов — наши заказы приходят «На согласовании», реализация
«по заказам» обычно ждёт «К отгрузке» (АРМ сам переводит или менеджер согласует);
поведение при нехватке остатка.

**Оценка:** малая-средняя. Готов выдать `ObjectModule.bsl` + структуру формы + шаги.

## 5. АРМ №5 — «QR-подключение агента» ✅ (УТ-часть проверена)

**QR штатно и в УТ (БСП `ГенерацияШтрихкода`, ТипКода=16), и в Моби-С.** Моби-С
(`НастройкаУстройства.ОбновитьQRСервер`) рисует QR через
`УправлениеПечатью.ДанныеQRКода(СтрокаQR, 0, 190)` и кодирует строку подключения:
`v=…&agId=<код агента>&srvE=<внешний адрес>&srvL=<локальный>&accId=<база>&accPwd=<пароль обмена>&dId=…`
— приложение сканирует и **самонастраивает связь**. При генерации агенту
назначается свободный ключ.

**Наш вариант (проще, токен-онбординг):** кодируем в QR `url сервера + разовый
короткоживущий токен привязки устройства`. Агент сканирует → приложение меняет
разовый токен на постоянный токен устройства (+ логин). Разовый токен — одноразовый,
не пароль открытым текстом.
- **УТ:** кнопка «QR для агента» → генерит разовый токен (в регистр рядом с
  `SmartSale_Токены`), рисует QR через БСП.
- **Сервер:** эндпоинт обмена разового токена на токен устройства (токен приходит
  обменом из УТ, как логины сейчас).
- **Приложение (клиент, ты собираешь APK):** экран сканера (CameraX + ML Kit/ZXing).

**Решить:** делаем сейчас (нужна доработка APK) или после АРМ. Вход по логину/паролю
остаётся запасным.

**Оценка:** УТ малая, сервер малая, сканер в APK средняя.

## 6. АРМ №1 — «Маршруты с интерактивной картой»

Маршрут у нас = агент + день недели + точки + порядок (`SmartSale_Маршруты`,
телефон показывает). Моби-С визиты ведёт документом `ЗаданиеТорговомуПредставителю`
(у нас — свой регистр, уже работает; см. развилку в §7).

**Как карта сделана у Моби-С (проверено по коду — переиспользуем схему):**
- **Технология — `Поле HTML документа` + Leaflet 1.5.1**, целиком заинлайненный в
  макет (leaflet.css/js, `esri-leaflet` для геопоиска, `polylinedecorator` для
  стрелок, плагин `L.Yandex`). Внешних CDN в рантайме нет — из интернета качаются
  только тайлы и геокодер.
- **Провайдер тайлов — OpenStreetMap** (`{s}.tile.openstreetmap.org/{z}/{x}/{y}.png`,
  без ключа) + слой Яндекс (`L.Yandex`, требует их JS/ключ) + базовые Esri; Google
  закомментирован. Поиск адреса — Esri geosearch.
- **Мост 1С↔JS:** *1С→карта* — через DOM `Элементы.ПолеБраузер.Документ`:
  `body.MarkerDraw(json)`, `body.SetCenter(lat,lng,zoom)`, `body.GetCenterNew()`;
  данные — ОДНА JSON-строка `{center, markers[], paths[], icons(base64)}`. *карта→1С*
  — карта «нажимает» скрытые `<input type=button>` (id-ы `MobiCCoordsUpdateBtn`,
  `MobiCClientSelected`…), 1С ловит в обработчике `ПолеБраузерПриНажатии` по
  `Button.id` и читает значения из скрытых `<input>`.
- **Рисование:** маркеры = `L.marker` + номер через `L.DivIcon`; маршрут = `L.polyline`
  со стрелками направления. Интерактив: **двойной клик** по карте → привязать
  координаты клиенту; **клик по маркеру** → выбрать клиента. **Перетаскивания
  маркеров нет** — координата задаётся кликом.
- **Координаты клиента — в штатной КИ** «Географическая широта/долгота» (тип
  «Другое», значение в представлении). Массовое проставление: «заполнить из
  партнёров/контрагентов/адресов доставки» + ручная привязка кликом + геокодер.
- **Порядок визитов Моби-С в 1С-части НЕ хранит** и **оптимизации маршрута (TSP)
  НЕТ** — агент строит порядок вручную. Значит порядок нам надо хранить **самим**
  (реквизит «НомерПоПорядку» в нашем маршруте), на карте рисовать нумерованными
  маркерами и линией со стрелками.

**⚠️ Главное ограничение — ТОЛЬКО ТОНКИЙ КЛИЕНТ (десктоп).** DOM-мост
(`Элементы.ПолеБраузер.Документ` + клики по скрытым кнопкам) работает во встроенном
браузере тонкого клиента; в **веб-клиенте так не работает** (нужен другой, урезанный
механизм HTML-поля), в мобильном клиенте 1С — не поддержит. Плюс тайлы/геокодер
требуют интернет с рабочего места оператора (у вас провайдер режет подсеть VPS —
тайлы идут с места оператора, не с сервера).

**Оценка честная:** повторяемо, средняя-большая сложность. Ядро — не 1С-код, а один
самодостаточный HTML/JS-макет с инлайн-Leaflet (его и собрать — основной труд); 1С
лишь гоняет JSON и ловит клики. **Решить:** провайдер (OSM бесплатно / Яндекс-ключ);
подтвердить, что оператор работает в тонком клиенте; нужна ли только визуализация
+ ручная привязка координат/порядка (реально) или ещё автопостроение (вне 1С,
отдельный сервис).

## 7. АРМ №2 — «Создание заданий»

**Развилка (важно): типовой документ vs наш объект.**
- **Моби-С**: задание = `Документ.ЗаданиеТорговомуПредставителю` (шапка агент+клиент+
  `ДатаВизитаПлан`+`Статус`, ТЧ «Задачи» с `ОписаниеЗадачи`/`Выполнена`/
  `ОписаниеРезультата`). Типы («Заказ», «ПКО», «Наличие и цены», «Задание с
  фотоотчётом», «Снять GPS»…) — строки задач.
- **Наше**: `SmartSale_Задания` (уже в обмене, телефон отмечает с фото/гео).
- ⚠️ Штатный документ требует **функциональную опцию** «Ведётся работа через
  торговых представителей» — в базе она **ВЫКЛЮЧЕНА** (проверил: `false`), а её
  включение тянет соглашения/условия обслуживания (ровно поэтому мы ушли на свой
  объект). **Рекомендую остаться на `SmartSale_Задания`** — переезд на типовой
  документ дорогой и без выгоды.

**Что взять у Моби-С (UX):**
1. **Мастер массовой постановки** (`ГрупповаяОбработкаЗаданий`): 5 шагов режим →
   агенты → клиенты → период → параметры; два способа — «период с шагом» и «в
   существующих визитах»; виды «Добавить»/«Удалить»; дедуп по (агент, клиент, дата,
   тип); флаги перезаписи; не трогать уже выполненные.
2. **Универсальный `ОтборКлиентов`** (СКД: контрагенты/партнёры/**сегменты**) +
   отбор агентов, сохранение настроек по пользователю; отбор агентов пересекать с
   правами супервайзера.
3. **Типы заданий — перечислением/справочником расширения** (у Моби-С хрупкие
   строки-литералы), с `ВремяОбслуживания` по типу.

**Решить:** типы/шаблоны заданий; нужна ли «цель визита» (ранее отложена); признак
массовой постановки (маршрут/сегмент/отбор). **Оценка:** малая-средняя.

## 8. АРМ №3 — «Формирование MML»

**Развилка: типовой `Ассортимент` (как Моби-С) vs свой список.**
- **Моби-С**: MML = штатный `РегистрСведений.Ассортимент` (измерения `ОбъектПланирования`
  =`ФорматМагазина`, `Номенклатура`; роль `ПостоянныйАссортимент` = must-stock),
  заполняется документами `ИзменениеАссортимента`. «Канал сбыта» = `ФорматыМагазинов`.
  Клиент → канал (один) через `ДополнительныеСведения`. Редактор — матрица
  «Номенклатура × Канал» с каскадом по иерархии, запись пачкой.
- **Наше (ранее согласовано)**: свой лёгкий механизм (справочник обязательных SKU
  по сегменту/категории) — потому что штатный `Ассортимент` пуст и у партнёра нет
  формата.
- **Переоценка:** Моби-С доказывает, что штатный `Ассортимент` РАБОЧИЙ, если его
  наполнить через АРМ (создать форматы-каналы, привязать клиентов доп.сведением,
  писать `ИзменениеАссортимента`). Плюс типового — интеграция с отчётами УТ и
  «ролью ассортимента»; минус — тяжелее, зависит от `ФорматыМагазинов`/`ИзменениеАссортимента`.
  Свой — проще и под контролем, но параллельная сущность.
- **Взять у Моби-С в любом случае:** **матричный редактор** «Номенклатура × сегмент/
  канал» (клик = назначить/снять, каскад по группам, запись пачкой в транзакции) —
  это удобный UX; движок покрытия MML на телефоне уже спроектирован (акции-подобный).

**Решить:** типовой `Ассортимент`+каналы (как Моби-С) или свой справочник; и по чему
привязка — сегмент клиента / категория точки / канал сбыта. **Оценка:** средняя.

## 10. Сквозные решения (реши один раз)

1. **Формат АРМ**: внешние `.epf` (как Моби-С — не трогают конфигурацию, легко
   грузить/обновлять) или объекты расширения. У нас уже есть расширение с обмена —
   АРМ можно делать `.epf`, читающими/пишущими наши объекты и типовые. Предлагаю
   **`.epf` на каждый АРМ**.
2. **Хранение настроек АРМ** (карты документов, параметры, реестр прав): по образцу
   Моби-С — `ХранилищеОбщихНастроек` со своим владельцем (`"SmartSale"`), без новых
   объектов метаданных. Данные (маршруты/задания/MML/токены) — в наших регистрах
   расширения (уже есть) или типовых (по развилкам 7/8).
3. **Права рабочих мест**: простой реестр «функций» + `ПроверитьРазрешение(ИмяФормы)`
   на входе (приём Моби-С) — вместо навешивания ролей платформы.
4. **Не занимать служебные имена** (Моби-С сам ошибся — занял `Параметры`); у нас
   это жёсткое правило.

## 11. Рекомендованный порядок

1. **№4 Реализация на основании** — максимум пользы, штатно, без карты/APK. Готов
   выдать исходники сразу.
2. **№2 Задания** — на нашем `SmartSale_Задания` + мастер массовой постановки и
   `ОтборКлиентов` от Моби-С.
3. **№3 MML** — сперва развилка (типовой Ассортимент vs свой), затем матричный
   редактор + движок покрытия на телефоне.
4. **№5 QR-подключение** — удобный онбординг (нужен сканер в APK).
5. **№1 Маршруты + карта** — самый тяжёлый (карта), когда прочее работает.
   Параллельно — кредит Фаза 2 и контроль доставки отдельными шагами.

## 12. Открытые вопросы (собрать утром)

- С какого АРМ стартуем (по умолчанию №4).
- №4: роль оператора; проводить сразу/черновик; кто переводит заказ «На согласовании»
  → «К отгрузке»; поведение при нехватке остатка.
- №2 задания: остаёмся на `SmartSale_Задания` (рекомендую) или переезд на типовой
  документ (дорого); типы/шаблоны заданий.
- №3 MML: типовой `Ассортимент`+каналы (как Моби-С) или свой справочник; привязка по
  сегменту/категории/каналу.
- №1 карта: провайдер тайлов (OSM бесплатно / Яндекс-ключ); подтвердить работу
  оператора в ТОНКОМ клиенте (карта в веб/мобильном клиенте не работает); нужен ли
  интернет на рабочих местах (тайлы/геокодер).
- №5 QR: делаем сейчас (нужен сканер в APK)?
- Формат АРМ: отдельные `.epf` (рекомендую) или расширение.
- Скриншоты/демо Моби-С по нужным АРМ — чтобы повторить UX.
