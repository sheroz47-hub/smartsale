# SmartSale — приложение для торговых агентов

Система приёма заказов в торговых точках: агент с телефоном работает офлайн,
офис ведёт каталог, остатки, отгрузку и дебиторку в веб-кабинете.

Задача — то же, что делает SmartUp: заказ снимается в точке, доезжает до
офиса, превращается в отгрузку, отгрузка становится долгом, долг гасится
оплатой.

## Состояние

Работает сквозной путь: агент входит с телефона, забирает справочники,
оформляет заказ без связи, заказ доезжает до сервера, офис подтверждает его,
резервирует товар и отгружает, долг клиента считается по отгрузкам и
оплатам. Проверено `tests/smoke.py` — все проверки проходят.

**Обмена с 1С нет.** Он вынесен в отдельный этап: API на стороне ERP и
Бухгалтерии для Узбекистана делается отдельно, сопоставление данных ведётся
там же. С нашей стороны у каждой сущности есть неизменяемый `uuid` — он и
служит ключом сопоставления.

**Android-приложение не собиралось.** Исходники написаны целиком, но
Android SDK на машине разработки нет, поэтому компиляцию оно не проходило.
Открыть в Android Studio, дать ей сгенерировать обёртку Gradle и собрать.

## Стек

Сервер: FastAPI + SQLAlchemy 2 + PostgreSQL 15, шаблоны Jinja2, Python 3.11+.
Телефон: Kotlin, Compose, Room, Retrofit, WorkManager, minSdk 24.

Выбран тот же стек, что в `tabel-web` и проекте ЗП — чинится теми же руками
и разворачивается тем же способом.

## Модель данных

Своя, не зеркало 1С. Ключевые решения:

**Деньги и количества — `Numeric`, не `float`.** `0.1 + 0.2` в двоичной
дроби даёт `0.30000000000000004`, и на накладной из тридцати строк это
вылезает расхождением, которое потом никто не может объяснить. На телефоне
по той же причине суммы хранятся строками и считаются `BigDecimal`.

**У документов с телефона есть `client_uid`.** Его генерирует телефон.
Связь на рынке рвётся посреди отправки, телефон повторяет запрос — без ключа
идемпотентности в базе появлялись бы двойные заказы.

**Долг не хранится полем, а считается запросом** — отгружено минус оплачено.
Хранимое сальдо рано или поздно разъезжается с документами, и тогда цифре в
карточке никто не верит.

**Отгрузка — отдельный документ, а не статус заказа.** Отгружают частями:
заказ на сто коробок закрывается тремя накладными в разные дни.

**Остаток лежит агрегатом в `stocks`, история — в `stock_moves`.** Без
истории расхождение остатка не расследуется: видно «сейчас минус три», но не
видно, кто их списал.

## Синхронизация

Односторонняя по каждому виду данных: справочники агент только читает,
документы только создаёт. При таком разделении слияния изменений не
возникает вовсе — а слияние и есть самое дорогое в офлайн-приложениях.

```
GET  /api/v1/sync/pull?since=<ISO>   справочники, изменившиеся после отсечки
POST /api/v1/sync/push               заказы, оплаты, визиты
GET  /api/v1/orders/state            что стало с ранее отправленным
POST /api/v1/auth/login              вход и привязка устройства
GET  /api/v1/ping                    проверка связи, без авторизации
```

Отсечка — всегда серверное время из прошлого ответа. Часы на телефонах
уходят на минуты, доверять им нельзя.

Время наружу отдаётся в UTC с суффиксом `Z`, а не `+00:00`: плюс в строке
запроса означает пробел, и клиент, забывший его закодировать, получал бы
отлуп на ровном месте. Разбор `since` этот случай всё равно переживает.

## Развёртывание

Прод — тот же сервер, ssh-алиас `deploy`, Debian 12.

| Что | Где |
|---|---|
| Код | `/srv/smartsale/app_src` |
| Виртуальное окружение | `/srv/smartsale/venv` |
| Настройки | `/srv/smartsale/.env`, права 600 |
| Служба | `smartsale.service`, слушает `127.0.0.1:8010` |
| Прокси | nginx |

Порт 8010 выбран, чтобы не столкнуться с проектом ЗП на 8000.

Первый запуск создаёт таблицы и учётную запись `admin` со случайным паролем —
он один раз пишется в журнал службы:

```bash
ssh deploy journalctl -u smartsale | grep 'пароль'
```

Обновление после правки:

```bash
scp -r app deploy:/srv/smartsale/app_src/ && ssh deploy systemctl restart smartsale
```

## Проверка

```bash
python tests/smoke.py
```

Поднимает временную базу SQLite, прогоняет весь путь от входа агента до
расчёта долга и удаляет её за собой. Боевая база — PostgreSQL, поэтому
«работает на SQLite» означает «логика цела», а не «на проде взлетит».

## Не сделано

- **Обмен с 1С.** Отдельный этап, см. выше.
- **Ведение справочников в кабинете.** Товары, склады и виды цен пока
  заводятся напрямую в базе; цены и остатки правятся из кабинета.
- **Миграции.** Схема создаётся через `create_all`. При изменении моделей
  перевести на alembic, иначе правки не доедут до существующей базы.
  На телефоне то же самое: в Room нужны миграции с первого же обновления —
  разрушающая пересборка уничтожит неотправленные заказы.
- **HTTPS.** Пока его нет, пароль агента ходит по открытому каналу, а в
  манифесте Android стоит `usesCleartextTraffic`. Появится домен — убрать.
- **Частичная отгрузка.** Документ отгрузки уже отдельный, так что она
  добавится строками с количеством меньше заказанного, не меняя схему.
- **Картинки товаров.** Поле есть, отдача и загрузка на телефон — нет.
- **Возвраты от клиента.**
