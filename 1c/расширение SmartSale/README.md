# Обмен SmartSale ↔ УТ. Этап 1: отдача справочников

Расширение конфигурации «Управление торговлей для Узбекистана 11.0.0.18»
с HTTP-сервисом, откуда сервер SmartSale забирает справочники.

Инициатор обмена — SmartSale. УТ сама наружу не обращается, записи в базу
на этом этапе нет вовсе: сервис только читает.

## Состав

| Файл | Что это |
|---|---|
| `HTTPServices/smartsale.xml` | описание HTTP-сервиса: корневой URL и шесть методов |
| `HTTPServices/smartsale/Ext/Module.bsl` | модуль сервиса, вся логика выгрузки и приёма |
| `CommonModules/SmartSale_Обмен/Ext/Module.bsl` | ядро приёма заказов и оплат (этап 2) |
| `../../../скрипты/smartsale/выпустить-токен.ps1` | выпуск токена авторизации канала |

## Как поставить в базу

Расширение собирается и загружается в Конфигураторе — это делается руками,
готового `.cfe` в комплекте нет намеренно: собранный вслепую файл труднее
проверить, чем три действия мышью.

1. Конфигуратор базы `ut_milk` → **Конфигурация → Расширения конфигурации**
   → добавить. Имя `SmartSale`, префикс `SmartSale_`, назначение
   **Дополнение**.
2. Открыть конфигурацию расширения, в ветке **HTTP-сервисы** добавить сервис:
   - Имя: `SmartSale_Exchange` — собственный объект расширения обязан
     начинаться с префикса, иначе Конфигуратор его не примет
   - Корневой URL: `smartsale` — именно он попадает в адрес, префикс на
     адрес не влияет
   - Повторное использование сеансов: **не использовать**
3. Добавить шесть шаблонов URL, у каждого один метод `GET`:

   | Шаблон | Метод | Обработчик |
   |---|---|---|
   | `/ping` | GET | `pingGET` |
   | `/meta` | GET | `metaGET` |
   | `/products` | GET | `productsGET` |
   | `/prices` | GET | `pricesGET` |
   | `/stocks` | GET | `stocksGET` |
   | `/customers` | GET | `customersGET` |

4. Открыть модуль сервиса и вставить в него содержимое
   `HTTPServices/smartsale/Ext/Module.bsl` целиком.
5. Обновить конфигурацию базы данных, перезапустить сеансы.
6. Опубликовать на веб-сервере (если публикация `ut_milk` уже есть —
   переопубликовать, чтобы новый сервис попал в список).

Если удобнее загрузить из файлов: `Конфигурация → Загрузить конфигурацию
из файлов`, выбрав каталог расширения. XML сервиса для этого готов, но
`Configuration.xml` расширения придётся взять из созданного пустого
расширения — его структура зависит от версии платформы.

## Пользователь для обмена

Завести отдельного пользователя 1С (например `smartsale`) **только с правом
чтения** нужных справочников и регистров. Не использовать администратора:
сервис отдаёт всю клиентскую базу и цены, и учётная запись для него не
должна уметь ничего менять.

## Методы

Все ответы — JSON в UTF-8. Числа передаются **строками**: JSON не различает
`1.10` и `1.1`, а разбор чисел с плавающей точкой добавляет погрешность.
Разделитель — точка, разрядов групп нет.

Ключ сопоставления — `uid`, уникальный идентификатор ссылки 1С. Он не
меняется никогда, в отличие от кода и наименования.

### `GET /ping`

Проверка живости, к данным не обращается.

```json
{"service": "smartsale", "protocol": "1.0", "server_time": "2026-09-16T12:00:00Z"}
```

### `GET /meta`

Организации, склады, виды цен и менеджеры одним ответом — их единицы.

Менеджеры берутся не из всего справочника пользователей, а только те, на
кого заведены клиенты. Отличить здесь торгового агента от администратора
нельзя: основным менеджером части партнёров стоит администратор — поэтому
поле называется `managers`, и кто из них агент, решает принимающая сторона.

Виды цен отдаются только пригодные для продажи (используется при продаже,
статус «Действует», не помечен на удаление). Тот же отбор применён к ценам,
чтобы в `/prices` не приехали ссылки на виды цен, которых нет в `/meta`.

### `GET /products?after=<uid>`

Номенклатура и группы. Группы приезжают вместе с элементами — приложению
нужно построить дерево.

### `GET /prices?date=<ГГГГ-ММ-ДД>`

Цены на дату, по умолчанию текущую. Источник — регистр
`ЦеныНоменклатуры25`: в этой базе работает ценообразование версии 2.5,
а старый регистр `ЦеныНоменклатуры` пуст.

Принимается и полная отметка вида `2026-09-16T12:00:00Z`, которую сервис
отдаёт сам в `server_time`. Дата без времени означает **конец суток**:
регистр периодичен посекундно, и срез на 00:00 не увидел бы цены,
введённые в этот день.

Отдаётся списком целиком, без страниц: цена привязана к паре
«товар — вид цены», и курсор по ней не строится.

### `GET /stocks`

Свободный остаток по складам: в наличии за вычетом зарезервированного
к отгрузке. Агенту нужно знать, что он может продать сейчас.

Выборка свёрнута по паре «товар — склад»: у регистра шесть измерений,
включая назначение, помещение и серию, и без свёртки на одну пару пришлось
бы несколько строк. Отдаётся списком целиком, без страниц.

### `GET /customers?after=<uid>`

Клиенты с контактами, координатами и кодом внешней системы. Координаты
берутся у контрагента — виды контактной информации для широты и долготы
заведены там, и передаются **строками** (`"41.2848554"`), как хранятся:
приведение к числу зависит от локали и ошибается тихо.

Контрагент выбирается один на партнёра, с приоритетом головного. Отсечь
обособленные подразделения нельзя: в базе **91 клиент**, у которого
контрагент существует, но помечен обособленным подразделением — иначе они
остались бы без ИНН, юридического наименования и координат.

## Постраничность

Курсором, а не смещением: в языке запросов 1С нет `OFFSET`.

Клиент передаёт `after` — `uid` последнего полученного элемента, выборка
упорядочена по ссылке и отдаёт то, что строго больше.

Применяется к `/products` и `/customers`. Ответ содержит `more` и `next`:
пока `more = true`, клиент повторяет запрос, подставляя `next` в `after`.
Размер страницы — 1000 записей, параметром не меняется.

У `/prices` и `/stocks` поля `more` и `next` есть ради единообразия разбора,
но всегда пусты: эти списки отдаются целиком.

Порядок обхода — двоичный порядок ссылок, а не хронологический. Элемент,
созданный во время выгрузки, может оказаться «до» курсора и на текущем
проходе не попасть в выдачу. Для полной перевыгрузки по расписанию это
безразлично, но опираться на такой порядок при переходе к инкрементальному
обмену нельзя.

```
GET /products                                → more=true,  next=<uid>
GET /products?after=<uid>                    → more=false, next=""
```

## Авторизация — по токену

К сервису обращается доверенный сервер SmartSale-посредник под одним
сервисным токеном. Токен идёт **своим** заголовком `X-SmartSale-Token: <токен>`,
а не `Authorization`: публикация 1С занимает `Authorization` под Basic —
двух значений в одном заголовке не бывает, поэтому токен идёт поверх Basic
отдельным заголовком. В базе хранится SHA-256 токена (регистр
`SmartSale_Токены`), а не сам токен.

Публикацию настроить так, чтобы веб-сервер **свою** аутентификацию не
требовал — единственный рубеж это токен. В `default.vrd` прописывается
служебная учётная запись 1С, под которой сервис работает всегда; у неё
право только на нужные объекты.

Выпуск токена — скрипт `выпустить-токен.ps1` в `C:\Users\User\скрипты\smartsale`:

```
powershell -ExecutionPolicy Bypass -File выпустить-токен.ps1 -Кому "SmartSale прод"
```

Он печатает **токен** (в настройку SmartSale, показывается один раз) и его
**хеш** (в регистр `SmartSale_Токены`: измерение «Хеш», наименование,
«Активен» = Да). Отзыв — снять флаг «Активен» или удалить запись.

Канал желательно вести по HTTPS (серверный сертификат на публикации), чтобы
токен не шёл открытым текстом. Клиентский сертификат при токенной
авторизации не нужен — mTLS не требуется.

## Проверка сервиса

`/ping` — без токена (проверка доступности), остальное — с токеном:

```
curl http://5.133.120.66:49900/ut_milk/hs/smartsale/ping
curl -H "X-SmartSale-Token: <ТОКЕН>" http://5.133.120.66:49900/ut_milk/hs/smartsale/meta
curl -H "X-SmartSale-Token: <ТОКЕН>" "http://5.133.120.66:49900/ut_milk/hs/smartsale/stocks?agent=<uid>"
```

Коды ошибок:

- **401** — нет токена или он недействителен/отозван.
- **400** — неверный параметр (`after`, `date`, `agent`) или тело запроса.
- **500** — сбой сервиса. Наружу только `trace_id`; текст ошибки 1С
  содержит имена таблиц и полей, а канал смотрит в интернет.

Подробности сбоев — в журнале регистрации, события `SmartSale.Обмен` и
`SmartSale.ПриемЗаказов`, по той же метке.

## Этап 2: приём заказов и оплат

Реализован приём заказов клиентов и приходных кассовых ордеров (оплат).

Создать регистры по пояснению в
`InformationRegisters/SmartSale_ЖурналПриема/Ext/пояснение.md`
(`SmartSale_СкладыАгентов`, `SmartSale_ЖурналПриема`, `SmartSale_Токены`) и
общий модуль `SmartSale_Обмен` (галка **Сервер**), текст —
`CommonModules/SmartSale_Обмен/Ext/Module.bsl`.

Заполнить `SmartSale_СкладыАгентов`: по строке на агента (пользователь →
организация, склад, подразделение, **касса**). Без записи заказы и остатки
агента отклоняются понятной ошибкой; без кассы отклоняются оплаты. Касса
агента должна вестись в валюте учёта (UZS) — иначе оплата отклоняется.

### `POST /orders?agent=<uid>`

Тело: `{"orders":[{client_uid, customer_uid, date, comment, lines:[{product_uid, qty, price, discount_amount}]}]}`.
Числа — строками. `agent` — uid пользователя-менеджера (из `/meta`).

- Заказ **проводится сразу** в статусе «На согласовании».
- Организация/склад/подразделение — из регистра агента; валюта, ставка НДС
  (12 %), операция «Реализация клиенту» — как в существующих заказах базы.
- Цена берётся из строки как есть (не пересчитывается). `discount_amount` —
  готовая сумма скидки на строку от движка акций SmartSale, садится
  **ручной скидкой**.
- Идемпотентность по `client_uid`: повтор возвращает прежний результат.
- Ответ: `{results:[{client_uid, status: accepted|rejected, number, error}]}`.

**Режим проверки** `?dryrun=1`: заказ заполняется и проводится в транзакции,
которая откатывается — боевого документа не остаётся. Нужен, чтобы отладить
заполнение и проведение на живой базе, не создавая заказов. **Начинать надо
именно с него.**

### `POST /orders/state`

Тело: `{"client_uids":["...","..."]}`. Ответ по каждому: принят ли, номер,
текущий статус заказа в УТ, отменён ли. Отслеживаются только заказы; оплаты
через этот метод не запрашиваются (у ПКО нет статуса).

### `POST /payments?agent=<uid>`

Тело: `{"payments":[{client_uid, customer_uid, amount, date, comment}]}`.
Числа — строками. `agent` — uid пользователя-агента (из `/meta`).

- ПКО «Поступление оплаты от клиента» **проводится сразу**.
- Оплата садится **в счёт общего долга клиента**: расшифровка платежа без
  привязки к заказу (`ОбъектРасчетов` не заполняется). Разнесение по
  заказам-долгам делает учётная система.
- Организация, касса, подразделение — из регистра агента; валюта — учёта
  (UZS). НДС с аванса не начисляется (`СтавкаНДС`/`СуммаНДС` не заполняются).
- Идемпотентность по `client_uid` (внутренний ключ с префиксом `pay:`, чтобы
  не пересечься с заказом того же uid): повтор возвращает прежний результат.
- Отклоняется понятным текстом, если у агента нет кассы, касса не в валюте
  учёта или у клиента нет контрагента.
- Ответ: `{results:[{client_uid, status: accepted|rejected, number, error}]}`.

**Режим проверки** `?dryrun=1` — как у заказов: ПКО проводится в транзакции,
которая откатывается. **Начинать надо именно с него.**

## Что НЕ делает этот этап

- не отдаёт долги клиентов — планируется отдельным методом;
- маршруты ведутся в SmartSale, не в УТ.
